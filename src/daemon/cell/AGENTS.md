## Durable Objects — general rules (read before creating any new Durable Object)

Canonical TurboPanel rules derived from [Cloudflare's Rules of Durable Objects](https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/). Apply to `DaemonCellObject` and any future Durable Object. Daemon-cell cost/hibernation detail lives in the sections below — do not duplicate it here.

### When to use a DO

Use a Durable Object for **stateful coordination** (shared mutable state, strong consistency, per-entity storage, long-lived WebSockets, per-entity scheduled work). Use plain Workers + Postgres/Hyperdrive for **stateless** request handling, globally distributed reads, and high fan-out. Never put a UI polling or fleet-wide read path behind a DO.

### Design

- **One DO per coordination atom** (daemon cell: one DO per `serverId`). Never a global singleton DO that funnels all traffic.
- **Deterministic ids** via `getByName(meaningfulId)`. Never `newUniqueId()` / `idFromName()` per attach. Enforced for the cell by `scripts/check-durable-object-hibernation.mjs` (`STABLE_ID_FILES`).
- **Throughput:** ~500–1000 req/s per DO for simple ops; shard (parent/child DOs) if a single atom will exceed that.
- **Parent/child** for hierarchical entities — parent tracks children; children own their own state so work parallelizes.
- **Location hints** optional for latency-sensitive creation; hints are suggestions, not guarantees.

### Storage

- **SQLite-backed only** (`storage: "sqlite"` / `new_sqlite_classes`). No legacy KV-backed DO storage.
- **Default init:** run migrations in the constructor with `ctx.blockConcurrencyWhile()`. Track schema versions with a table (DO SQLite rejects `PRAGMA user_version` for writes — see `_cell_schema` below).
- **Daemon-cell deviation (intentional):** `#ensureSchema()` is **lazy**, not constructor-`blockConcurrencyWhile`, so `/rpc/diagnostics` and `/rpc/liveness` stay at **zero SQLite** on cold wake. See "DO storage schema" below. New DOs should prefer constructor migrations unless they have the same cold-wake zero-storage constraint.
- Persist important state to SQLite; in-memory class fields are cache only (lost on eviction/crash).
- **Indexes:** create indexes for frequently filtered columns. **Daemon cell:** secondary indexes on `request.delivery_status` / `request.status` are **evaluated and deferred** — each DO's `request` table is one server's in-flight work (small/bounded); revisit if row counts grow.
- Rely on **input/output gates** and write coalescing (avoid `await` between related storage writes). Prefer `transaction()` over per-request `blockConcurrencyWhile()`.
- Non-storage I/O (`fetch()`, Hyperdrive, R2) opens the input gate — use optimistic locking / check-and-set across those awaits.
- Use `blockConcurrencyWhile()` **sparingly** (init/migration only). Never across slow external I/O on every request.

### Communication

- Cloudflare recommends **native RPC methods** on the DO class (compat date ≥ `2024-04-03`). **Daemon-cell deviation (intentional, revisit later):** the cell still uses **`fetch()`-based RPC** (`do-registry.ts` `#rpc` → `/rpc/…`) — large cross-cutting refactor for ergonomics/type-safety with no functional bug today.
- Always **`await`** stub/RPC calls (no dangling promises).
- If a DO must know its own identity, expose an explicit `init()` (DOs do not learn their name from inside).

### Error handling

Every public DO entry point — `fetch`, `webSocketMessage`, `webSocketClose`, `webSocketError`, `alarm` — must have an **exception boundary**. House style: `fetch` → try/catch around `#handleRpc` → `errorResponse(..., 500)`. WS handlers **log and swallow** so a bad message/cleanup failure does not terminate the instance; `alarm` **logs and rethrows** so Cloudflare's alarm retry/backoff still runs. Mirror the WS swallow pattern on the Redis/Deno inbound path (`deno-ws.ts` `handleInboundMessage`).

### WebSockets and alarms

- **Hibernation API only** (`ctx.acceptWebSocket`); never `server.accept()`. Persist per-connection state with `serializeAttachment` / `deserializeAttachment`.
- With `web_socket_auto_reply_to_close` (compat ≥ `2026-04-07`), the runtime auto-completes the close handshake; calling `ws.close()` in `webSocketClose` remains safe.
- Alarms: **idempotent** handlers; schedule only when there is real work; `setAlarm` = billed row write (skip when target unchanged). Full wipe via `storage.deleteAll()` (and `deleteAlarm` first on older compat dates). Design for unexpected shutdowns — write progress as you go; no shutdown hooks.

### Testing and class lifecycle

Use `@cloudflare/vitest-pool-workers` (`runInDurableObject`, `runDurableObjectAlarm`, typed stubs). Class rename/delete goes through Wrangler `exports` (`state: "renamed"` / `"deleted"`). See `src/daemon/durable-object.test.ts`.

### Redis / self-hosted parity

Workers DO mechanics with **no Redis analog** (document only): hibernation API, alarms-as-billed-rows, `blockConcurrencyWhile`, SQLite indexes, native vs `fetch` RPC.

**Must stay behaviorally mirrored** in `src/daemon/cell/redis/cell.ts` and `src/daemon/deno-ws.ts`:

- One coordination atom per entity + deterministic keys (`tp:cell:{serverId}:*`)
- Exception boundaries on inbound message handling
- Idempotent maintenance / retries (`maintain()` is already `.catch`'d at the `deno.ts` timer)
- Always-await; no non-atomic race windows across external I/O; write-as-you-go

Any DO behavioral change must be checked against `src/daemon/cell/contracts.ts` (`DaemonCell`) and the Redis implementation updated in the same change. User-facing API and status semantics stay identical on both runtimes (see Parity callout under Daemon Cell).

### Checklist — creating a new Durable Object

1. Pick **one** coordination atom; route with `getByName()`.
2. Declare `storage: "sqlite"` in `wrangler.jsonc` `exports` / migrations.
3. Prefer constructor `blockConcurrencyWhile` migrations (lazy schema only with a documented cold-wake reason).
4. Add the source file to `DO_HOSTED` in `scripts/check-durable-object-hibernation.mjs` if it uses hibernation/alarms.
5. Wrap all public entry points in try/catch (WS swallow / alarm rethrow).
6. Add a Vitest suite in the `durable-object.test.ts` style.
7. If there is a self-hosted analog, design Redis (or equivalent) parity alongside and document billing/parity trade-offs in a subsystem `AGENTS.md`.

## Daemon Cell (`/ws/daemon/v1`)

> **Cost warning:** Durable Objects and Redis are scarce, billable, and cost-sensitive resources. Keep the cell lean — it owns live connection state and projects meaningful changes to Postgres; never use DOs/Redis as UI polling or read APIs. Never fan one dashboard page into one DO/Redis request per server; use Postgres/Hyperdrive for cheap status reads. Avoid heartbeat write amplification and per-viewer cell invocations. Any new cell RPC must justify why Postgres, cache, or a normal API cannot serve the use case. TurboPanel is bootstrapped and must protect Cloudflare costs aggressively.
>
> **Durable Object hibernation (Workers):** DO GB‑sec billing explodes when the object stays awake. **Never** use `setInterval` / `setTimeout` / `scheduler.wait` inside the cell — schedule work with `ctx.storage.setAlarm()` only for genuine pending work (outbox pump, request expiry, terminal retention); skip `setAlarm` when the target is unchanged. **Never** use standard `server.accept()` — attach with `ctx.acceptWebSocket()` and the hibernation WebSocket API so idle sockets do not keep the DO hot. **Never** run polling loops, long-running `await`s, or unresolved promises inside DO handlers; finish each RPC quickly and return so the object can hibernate. **Always** close outbound Hyperdrive/postgres.js connections in a `finally` block — an open DB socket prevents hibernation. **One stable DO id per server** via `getByName(serverId)` — never `newUniqueId()` / `idFromName()` per attach. Heartbeat Postgres projection opens only for daemonBuild change, `timeSync`/`resources.ips`/`docker` presence facts, or runtime/offline repair — elapsed coalesce time alone never opens Hyperdrive. Enforced in `src/daemon/cell/do.ts` (banner + `#withProjectionDb`) and `src/daemon/ws-handlers.test.ts` (source scan).

### Durable Object billing model (SQLite-backed)

TurboPanel daemon cells use SQLite-backed Durable Objects — do not add legacy KV-backed Durable Object storage pricing.

**Compute (Workers Paid):** Requests 1M/mo included then $0.15/M — billing includes HTTP requests, RPC sessions, WebSocket messages, alarm invocations; WebSocket connection establishment counts as a request; **incoming** WS messages billed 20:1 (100 incoming = 5 billable); outgoing WS messages and protocol pings not charged. Duration 400,000 GB-s/mo included then $12.50/M GB-s, billed at 128 MB/DO; a DO incurs duration while executing JS or idle-but-not-hibernatable; standard `accept()` sockets bill for the full connection lifetime, so use the Hibernation API for idle daemon sockets; `state.setWebSocketAutoResponse()` auto-responses add no wall-clock time.

**Compute (Workers Free):** 100,000 requests/day; 13,000 GB-s/day.

**SQLite storage (Workers Paid):** Rows read first 25B/mo then $0.001/M; rows written first 50M/mo then $1.00/M; SQL stored data 5 GB-month then $0.20/GB-month. KV-style `get()/put()/delete()/list()` are hidden SQLite tables billed as rows read/written; **each `setAlarm()` = 1 row written**; **deletes count as rows written**; stored data billable until removed.

**SQLite storage (Workers Free):** 5M rows read/day; 100,000 rows written/day; 5 GB total.

### Anti-regression rules (daemon cell)

- SQLite-backed DOs only; no legacy KV pricing/guidance.
- Never use DO storage as a polling scratchpad.
- No recurring heartbeat writes unless product correctness requires it; prefer WS lifecycle events + hibernation.
- Never call `storage.list()` (or table scans) in hot paths without documenting why.
- Don't repeatedly read cell metadata for every ping/message; cache stable cell state in memory after init.
- Treat `setAlarm()` as a row write (only call when the target changes).
- Document every new storage key/table/column; any new storage op must state its billing impact.
- Any WS code must preserve hibernation eligibility unless documented.
- **Every DO DB op must be time-bounded.** Wrap Hyperdrive/postgres.js work in `runWithDbTimeout` (`src/db.ts`, hard `DB_OP_TIMEOUT_MS` = 8 s client-side deadline) and always close the pool in `finally`. Never `await` an unbounded DB round-trip inside the DO or hand one to `ctx.waitUntil` — a stalled connect/query holds the object non-hibernatable and bills wall time for the **entire WebSocket lifetime** (root cause of a 71-min / ~547 GB-s single-socket incident: `#projectConnected` → `#withProjectionDb` hung with 0 CPU). The `do.ts` source-scan guard (`ws-handlers.test.ts`) asserts `runWithDbTimeout` + `endDbConnection` stay present. `createWorkersDb` also sets `connect_timeout` + `statement_timeout` as defence-in-depth; the DO projection factory passes the tightest values.
- **Every non-DB background/await in the DO must also be time-bounded — not just DB ops.** `raceWithTimeout` (`src/db.ts`, generic sibling of `runWithDbTimeout`) bounds work that isn't a Postgres call: `#getDaemonJwtKeyring()` on the WS-upgrade path (awaited directly, so a stuck derivation now fails fast with `503` instead of blocking the upgrade), and every `#pumpOutboxToDaemonSockets` call site, which used to be fired as a bare `void this.#pumpOutboxToDaemonSockets(...)` — a genuinely dangling, un-awaited, un-bounded promise inside a DO handler (the exact anti-pattern the hibernation banner above warns against). `#runBoundedBackground` (`do.ts`) now wraps those in `ctx.waitUntil(raceWithTimeout(...))` with a 5 s deadline (`BACKGROUND_TASK_TIMEOUT_MS`) and logs `daemon-cell event=background-timeout label=… serverId=…` on timeout. `raceWithTimeout`'s timer lives in `db.ts`, not `do.ts`, for the same reason `runWithDbTimeout`'s does — the source-scan guard forbids a literal `setTimeout`/`setInterval` in `do.ts` itself. Added after a billing audit found 0 `exceededWallTime` DO invocations in the 24 h before a push vs. 16 (≈53 GB-s, ~30 s each, near-zero CPU) in the 24 h after, with zero `"... projection failed ..."` logs — i.e. the DB guard above was intact and never fired, so the hang was in one of these previously-unguarded, non-DB paths.
- JWKS must never expose raw platform secrets; daemon-verifiable JWTs use public verification material (asymmetric).

> **Parity:** Cloudflare Workers (Durable Object) mode and self-hosted Deno/Redis mode must keep behavioral parity. DO and Redis are implementation details only — the user-facing API and status semantics are the same on both runtimes.

**WebSocket watchdog (Workers cost cap):** the DO cannot self-terminate a socket that stays awake via some unforeseen path, so the once-a-minute offline-sweep cron's read-only `checkLiveness` (`/rpc/liveness`) also force-closes unhealthy daemon sockets before reporting presence — `#reapUnhealthySockets` + the pure policy in `src/daemon/cell/socket-health.ts` (`evaluateSocketHealth`). Two triggers: **half-open** (auto-response/cell-ping older than `HALF_OPEN_CLOSE_MS` = 150 s, safely above the 60 s ping cadence) and an absolute **max age** (`MAX_WS_CONNECTION_AGE_MS` = 2 h) as a catastrophic backstop. Attach stores `connectedAtMs` in the serialized attachment for the age check. Closing is in-memory only (no SQLite, hibernation-safe); the normal `webSocketClose` path then runs lease cleanup + Postgres demotion, and the daemon reconnects (full-jitter backoff + connect rate limit). This adds **no** per-DO periodic alarm — it reuses the existing cron so there is no recurring row-write cost. Greppable: `daemon-cell event=watchdog-close serverId=… reason=half_open|max_age`. Because healthy servers are no longer woken every minute (AE short-circuit — see Offline sweep below), `#reapUnhealthySockets` now runs only on **AE-flagged suspects** still visited by `checkLiveness`. The absolute `MAX_WS_CONNECTION_AGE_MS` (2 h) cap is now **primarily enforced daemon-side** via a self-recycle (see daemon `AGENTS.md` Idle presence); the instance-side max-age check remains only as the suspect-path backstop.

**Daemon rate limiting (Workers + Deno):** two Wrangler `ratelimits` bindings gate reconnect storms and expensive daemon REST before the cell does work. Counters are account-global for a shared `namespace_id`, so each env uses distinct ids:

| Binding | Purpose | dev `namespace_id` | testing | live | `simple` |
| --- | --- | --- | --- | --- | --- |
| `DAEMON_CONNECT_RATE_LIMITER` | WS upgrade / reconnect storms | `"1001"` | `"2001"` | `"3001"` | `{ limit: 6, period: 60 }` |
| `DAEMON_REST_RATE_LIMITER` | enroll / challenge / session / lease / decrypt | `"1002"` | `"2002"` | `"3002"` | `{ limit: 30, period: 60 }` |
| `DAEMON_METRICS_RATE_LIMITER` | host-metrics ingest (~1/min/server) | `"1004"` | `"2004"` | `"3004"` | `{ limit: 3, period: 60 }` |

Keys use stable identifiers (`serverId` / `licenseId`, or the `enroll-challenge` sentinel for anonymous enrollment challenges), never IP — see `src/daemon/rate-limit/keys.ts`. Metrics uses `daemonMetricsRateLimitKey(serverId)` on the dedicated limiter. Workers resolution lives in `resolveWorkersDaemonRateLimiters` (`workers-bindings.ts`); absent bindings **fail closed** on production-like Workers and stay noops only on the explicit dev surface / tests. After JWT verify on `GET /ws/daemon/v1`, a failed connect limit returns **429** before `DAEMON_CELL.getByName` so the Durable Object never wakes. REST returns `{ ok:false, error:"rate_limited" }` with **429**. Inside the DO, an in-memory per-`connectionId` inbound-message cap (`TURBOPANEL_DAEMON_WS_INBOUND_LIMIT` default 120 / `TURBOPANEL_DAEMON_WS_INBOUND_WINDOW_MS` default 60000) drops floods without timers (auto-response pings never hit `webSocketMessage`). Inbound frames are also size-validated via `validateDaemonInboundFrame` before `recordInbound` / storage work — oversized or malformed frames close with policy-violation `1008`.

**Deno/Redis parity** shares the same `RateLimiter` interface and keys (`daemonConnectRateLimitKey` / `daemonRestRateLimitKey` / `daemonMetricsRateLimitKey`). `createRedisRateLimiter` (`src/daemon/rate-limit/redis-rate-limiter.ts`) implements an atomic token-bucket Lua script under `tp:ratelimit:*` (`rateLimitKey` in `src/daemon/cell/redis/keys.ts`); `deno.ts` wires connect + REST + metrics limiters from the existing Redis cell client into `registerDaemonWebSocket` / `registerDaemonApiRoutes`. Limits are env-tunable via `TURBOPANEL_DAEMON_CONNECT_RATE_LIMIT` / `TURBOPANEL_DAEMON_CONNECT_RATE_PERIOD` (defaults `{6,60}`), `TURBOPANEL_DAEMON_REST_RATE_LIMIT` / `TURBOPANEL_DAEMON_REST_RATE_PERIOD` (defaults `{30,60}`), and `TURBOPANEL_DAEMON_METRICS_RATE_LIMIT` / `TURBOPANEL_DAEMON_METRICS_RATE_PERIOD` (defaults `{3,60}`); Redis errors **fail open** on daemon limiters (`onError` default `'open'`) so a hiccup never locks out daemons; client-auth Redis throttling uses `onError: 'closed'` so login/OTP/install never fail open into unthrottled. Inbound floods use the shared pure gate in `src/daemon/rate-limit/inbound-window.ts` (same `TURBOPANEL_DAEMON_WS_INBOUND_*` defaults as the DO). Deno also counts the wire `DAEMON_CELL_PING` against that gate because each ping does real Redis `recordInbound` work (unlike the free Workers auto-response).

Server nodes are tracked by a **Daemon Cell** abstraction keyed by `serverId`. There is no authoritative daemon state in the main instance process or UI read path — presence, outbox, and pending request records live in the cell backend (Redis or DO SQLite), and UI/API status reads come from Postgres. The cell implementation intentionally caches stable runtime state in memory after initialization (`#serverId`, `#runtimeConnected`, live WebSocket attachments on Workers; Redis meta HASH for the same fields on Deno) and persists only the documented SQLite/Redis columns below. Do **not** reintroduce `connection_id` or `connected` as persisted cell columns — they belong in memory, WS attachments, and (on Redis) the meta HASH only.

| Runtime | Backend | Storage |
| --- | --- | --- |
| Deno (self-hosted) | `RedisDaemonCell` (`src/daemon/cell/redis/`) | Redis Streams + HASH + SET at `tp:cell:{serverId}:*`; Unix socket `/run/turbopanel/redis.sock` |
| Cloudflare Workers | `DaemonCellObject` (`src/daemon/cell/do.ts`) | SQLite-backed Durable Object per server, named by `serverId` |

Wrangler declares the Workers Durable Object lifecycle with `exports` in `wrangler.jsonc` (`DaemonCellObject`, SQLite). The Cloudflare dashboard lists that namespace as `instance_DaemonCellObject` because the live Worker script is named `instance` — `{script}_{class}` is display only, not a separate class.

Postgres remains canonical for business data (`server`). The cell is the low-latency hot projection and coordination layer for **presence only** — no monitor tables, no monitor wire payloads, and no HTTP heartbeat ingestion path.

**Postgres status read model:** just two dedicated `server` columns — `is_connected` (boolean) and `status_changed_at` (last `is_connected` flip, online **and** offline) — hold the UI/API liveness read model. There is no `daemon_status`, `last_seen_at`, `connected_at`, or `disconnected_at` column; `connectedAt` is derived (`statusChangedAt` while `is_connected`, else `null`) and the tri-state `online|offline|unknown` label is computed at the API layer (`mapServerDaemonStatusFromColumns` in `src/daemon/authn/daemon-state.ts`), not stored. Default status reads are Postgres-only (no read-time `getSnapshots`): `GET /api/client/v1/servers`, `GET /api/client/v1/servers/status`, and `GET /api/client/v1/servers/:id/status`. `GET /api/client/v1/servers/:id/cell` is admin/debug-only and reads live cell snapshots (`withSnapshots: true`).

**Presence model:** daemons send `{ type: "hello", at, daemonBuild }` once on connect. After ~60 s of inbound silence they send the wire cell ping (`DAEMON_CELL_PING`) only — **ping-only steady state** on Workers (zero DO SQLite writes/min for an idle connected server). App-level `{ type: "heartbeat", at, daemonBuild?, timeSync?, resources?, docker? }` follows when the daemon build commit changed (after an update) **or** when `timeSync`/`resources.ips`/`docker` differ from the last-sent snapshot (change-detected, still cadence-bound to the idle tick). Clean disconnects mark offline immediately via attach/close. On **Workers**, offline detection is **disconnect-first** via `webSocketClose`/`webSocketError` → `#cleanupWebSocket`; there is **no periodic stale-sweep alarm**. A silent half-open socket self-heals on reconnect (lease force-detach) or command dispatch (outbox requeue → consumer timeout). `#collectStaleDemotions` (`DAEMON_OFFLINE_SWEEP_MS`) is an opportunistic backstop that runs only when `alarm()` already fired for real work — it derives staleness from `getWebSocketAutoResponseTimestamp`, not SQLite `last_seen_at`. On **Redis (Deno)**, timer-driven `maintain()` + `sweepStalePresence` (`DAEMON_CELL_MAINTAIN_MS`, demote at `DAEMON_OFFLINE_SWEEP_MS`) remains the offline path — cost-safe because there is no DO billing. `DaemonCellSnapshot` holds `connected`, `connectedAt`, `lastInboundAt`, `lastSeenAt`, and optional `daemonBuild`. On Workers, presence timestamps (`connectedAt` / `lastSeenAt` / `lastInboundAt`) and `daemonBuild` live in the **Postgres projection** (status columns / `server.daemon.projection`) — the trimmed SQLite `cell` row only stores `server_id`, `remote_address`, `key_last_used_at`, and `updated_at` (no `last_seen_at`). Attach/detach update in-memory + WS attachment state and project connect/disconnect to Postgres; steady-state hello/heartbeat do not write SQLite `cell` rows. Projection debounce for inbound hello/heartbeat uses per-isolate in-memory `#lastProjectedAtMs` / `#lastKnownDaemonBuild` instead of the removed `last_projected_at` column.

**Offline sweep (Workers, ungraceful disconnects):** a hard power-off or network partition never fires `webSocketClose`/`webSocketError`, so the disconnect-first path above never runs and the DO happily reports "connected" until something else notices — Cloudflare will eventually reap the dead socket, but on no fixed schedule. `src/daemon/cell/offline-sweep.ts` closes that gap with a Cron Trigger (`wrangler.jsonc` `triggers.crons`, `"* * * * *"` — 60s, Cloudflare's finest cron granularity) that every tick: (1) reads servers Postgres currently believes are `is_connected` (`listConnectedServersForSweep`) plus recently-offline rows for self-heal (`listRecentlyOfflineServersForSweep`), (2) applies **deterministic rotation** (`rotateSweepBatch` in `postgres-projection.ts`) with separate budgets for connected stale-checks (`CONNECTED_SWEEP_BUDGET` 700) and recently-offline self-heal (`SELF_HEAL_SWEEP_BUDGET` 200) so self-heal candidates are not starved by connected rows, (3) runs **one fleet-wide Analytics Engine SQL read** (`queryRecentlyActiveServerIds` in `src/daemon/metrics/analytics-engine/sql-api.ts`, window `AE_LIVENESS_WINDOW_SECONDS` = 180 s) resolved via `resolveAnalyticsEngineSqlConfig` — connected servers present in the recent-host-sample set are **provably alive and skip the `checkLiveness()` DO wake entirely** (zero subrequests), while **suspects** (absent from AE) keep the existing `checkLiveness → isStale → onDaemonDisconnected` path; recently-offline self-heal splits into AE-direct heal (`onDaemonConnectedFromEvidence` — Postgres-only, no DO wake / no `getSnapshot`, only when the AE latest sample is strictly newer than `offlineAt` — derived solely from `statusChangedAt` (there is no separate `disconnectedAt` column) — so a pre-disconnect metrics sample inside the 180 s window cannot undo a clean offline projection) vs probed heal (`onDaemonConnected` after `checkLiveness`), both still bounded by `SELF_HEAL_SWEEP_BUDGET`, (4) for suspects, fans out a **read-only** `checkLiveness()` RPC (`DaemonCell.checkLiveness`, `do.ts` `/rpc/liveness`) — it only reads the runtime-tracked WebSocket auto-response timestamp (`ctx.getWebSocketAutoResponseTimestamp`, the same value the free `DAEMON_CELL_PING`/pong keeps warm) and never touches SQLite — then demotes stale connected servers via `onDaemonDisconnected(db, serverId, cell, "sweep_stale")` (reusing the existing projection, with a dedicated transition reason distinct from a clean client-initiated `"disconnect"`) plus `notifyServerWentOffline`, and **self-heals** live+warm servers Postgres still marks offline via `onDaemonConnected`. The cron-only isolate never runs `initWorkerApp`, so `runOfflineSweep` registers a write-only status-event sink itself (`setServerStatusEventSink(resolveServerMetricsStore(...))`) before sweeping — sweep-driven demotions and self-heals emit the same status events (`reason: "sweep_stale"` / `"self_heal"`) as the interactive `webSocketClose` / hello paths. **Fallback:** when AE config is missing or the query throws (`sweepOnceFallback`), the sweep reverts to today's check-all so offline detection is never lost. Greppable: `offline-sweep event=ae-liveness|ae-unavailable|ae-query-failed`. Null-ping grace uses in-memory first-null observation bookkeeping per cron isolate (`firstNullObservedAtMs` in `offline-sweep.ts`) — a live socket whose auto-response timestamp is still null is never demoted on its first sweep observation, even when Postgres `connectedAt` is old; after the marker ages past `OFFLINE_SWEEP_STALE_MS`, demotion proceeds. Fan-out is capped at `MAX_SWEEP_FANOUT` (900 total across both budgets, under the Workers-paid 1000-subrequest-per-invocation ceiling) and bounded to `FANOUT_CONCURRENCY` (25) in-flight RPCs at a time; servers beyond the per-tick budget — including those skipped when the wall-clock deadline is reached — are picked up on later ticks via `rotateSweepBatch`. Concurrent cron isolates share a Postgres `setting`-table CAS lease (`OFFLINE_SWEEP_LOCK`, TTL `OFFLINE_SWEEP_LEASE_MS` ≈ 90 s) so a second tick skips (`event=skipped-lease-held`) instead of doubling DO wakes and Hyperdrive clients — no KV, D1, R2, or DO storage, so no new Cloudflare line item. `expiresAt` is `max(now + TTL, tick deadline + DB_OP_TIMEOUT_MS)` so a still-running holder cannot be stolen mid-invocation even after the nominal 90 s TTL; crash recovery still steals once that enforced live runtime has elapsed. Each tick is also bounded by `OFFLINE_SWEEP_TICK_BUDGET_MS` (≈ 45 s) as a **hard deadline**: every awaited phase (`demote` / `heal` / `heal-direct`, optional `command-dispatch` / `webhook-deliveries` / execution-log R2 retention / `system.reconcile` + leaf renewal, and lease acquire/release) is wrapped with remaining-time `raceWithTimeout` or `runWithDbTimeout`; a timed-out phase logs `event=budget-exhausted phase=…` and does not start later work (`DEMOTION_RESERVE_MS` is held back so already-probed demotions/heals still write). External awaits are hard-capped: AE SQL `AbortSignal.timeout(AE_LIVENESS_QUERY_TIMEOUT_MS)` (≈ 5 s), each `checkLiveness` RPC `raceWithTimeout(LIVENESS_RPC_TIMEOUT_MS)` (≈ 5 s), and candidate-list reads `runWithDbTimeout` (`DB_OP_TIMEOUT_MS` = 8 s). Execution-log retention is gated on `controller.scheduledTime` every `EXECUTION_LOG_SWEEP_MINUTE_DIVISOR` (15) minutes — dispatch / webhook `DELETE`s stay every tick. Empty candidate lists return before the AE query (`event=no-candidates`). `scheduled()` awaits the sweep so Cron Trigger observability records real duration. Greppable also: `skipped-lease-held`, `no-candidates`, `budget-exhausted`, `tick-complete`. This does **not** reintroduce a per-DO recurring alarm — every `setAlarm()` reschedule is a billed SQLite row write (see "Alarm / hibernation" below and the DO billing model), so centralizing the "when to check" clock in one Cron Trigger keeps cost proportional to churn, not fleet size. Redis/Deno does not need this cron — it already has `sweepStalePresence` above. Detection latency: one cron tick plus the stale grace, plus at most one skipped tick when a lease holder crashes before expiry (TTL is just above the tick budget, not two full cadences). The same cron invocation also runs the `system.reconcile` drift sweep (`runSystemReconcileSweep`) on the already-open `db` (no second Hyperdrive client, no new per-DO alarm); Deno's maintenance timer has parity alongside `sweepStalePresence` (liveness `maintain` + `sweepStalePresence` and slower cleanup use **separate** in-flight flags via `createDenoMaintenanceScheduler`, so a hung dispatch/webhook/execution-log/reconcile phase cannot suppress the next stale-presence tick — each lane still refuses to overlap itself).

**Sparse Postgres projection:** connect/disconnect transitions and meaningful heartbeats (daemonBuild change or `timeSync`/`resources.ips`/`docker` facts — never time-only) project to the two status columns via `onDaemonConnected` / `onDaemonDisconnected` / `onDaemonHeartbeat` (`control-plane-monitor.ts` → `postgres-projection.ts`). There is no periodic time-only touch write — a heartbeat with no daemon-build-commit change and no new `timeSync`/`resources.ips`/`docker` facts writes nothing. Daemon build identity from `hello` is stored on `server.daemon.projection`; hostname/machineKey also land on dedicated columns. `ServerFleetPresence` in `server-status.ts` exposes the read model for routes (`connectedAt` only while online; `statusChangedAt` for both online and offline transitions). Every genuine `is_connected` flip (never a heartbeat/identity/daemonBuild touch) also fires a fire-and-forget **status event** to the per-runtime `ServerStatusEventSink` (`emitServerStatusEvent` — see `src/daemon/metrics/AGENTS.md`) for history-only uptime/downtime analytics; this event stream never gates or backs the Postgres read model above.

**Server geolocation (Workers-only today):** connecting-IP geo is persisted on `server.metadata.geo` (`ServerGeo` in `src/lib/geo/server-geo.ts`). **Cloudflare Workers** resolve geo from `request.cf` via `extractCloudflareGeo()` in `src/daemon/workers-ws.ts`, stamp `X-Turbopanel-Cell-Geo` onto the DO upgrade, and persist the same object on the hibernation WebSocket attachment so the first `hello` can backfill if the attach `waitUntil` connect projection races. **Self-hosted Deno** calls `resolveSelfHostedGeo()` in `src/lib/geo/self-hosted-geo-provider.ts` on connect but always returns `null` — there is no bundled IP lookup on managed/self-hosted installs yet (co-located dev uses `__direct__` / Unix socket anyway). Projection (`geoRefreshDue` in `postgres-projection.ts`) writes geo when incoming geo exists and stored `metadata.geo` is missing/invalid, or when `remoteAddress` changes; `geoEquals` ignores `capturedAt` so timestamp-only churn does not rewrite Postgres. Metadata geo writes use Postgres `jsonb ||` merges (`projectServerDaemon`) so concurrent `touchServerMetadata` resource patches cannot wipe `metadata.geo`.

**Host OS (`server.os_*` columns):** daemons send an `os` block on WS `hello` (from `/etc/os-release`, plus point-release / Raspberry Pi detection). Deno WS and the Workers DO hello path call `touchServerMetadata` to map it onto `os_id` / `os_family` / `os_version` / `os_codename` / `os_pretty_name` / `os_architecture` (Raspberry Pi OS → `os_id = raspberry-pi-os`). `resolveFleetPresence` composes the nested `os` object for the API. `GET /api/client/v1/servers` returns `os`, `osDisplay` from `formatServerOsDisplay()` (e.g. `"Debian 13.5 (Trixie)"` / `"Raspberry Pi OS 12.11 (Bookworm)"`), and `osLogo` (`debian` | `raspberry-pi-os` | null) from `resolveServerOsLogoKey()`.

**Host time-sync + addresses (`server` timezone/NTP columns + `metadata.resources.ips`):** daemons send `timeSync` and nest addresses on `resources.ips` on WS `hello` and on change-detected `heartbeat` frames. Deno WS and the Workers DO presence path persist via `touchServerMetadata` (OS/time-sync columns + jsonb `||` for `resources` / `docker`; unchanged facts skip the write). Heartbeat `{ resources: { ips } }` must not drop hello-only cpus/gpus/memory/swap. `resolveFleetPresence` composes `timeSync` / `ips` for the API. Successful `server.timezone.set` / `server.ntp.set` command outcomes also refresh the time-sync columns immediately via the command consumer.

**Host inventory (`server.metadata.resources` cpus/gpus/memory/swap):** daemons send capacity on WS `hello` only — `cpus[]` (one entry per socket: `vendorId`, `name`, `cores`/`threads` with optional `p`/`e`, `cache` bytes, `speedMhz`/`turboMhz`) and `gpus[]` (DRM `cardN`: name, PCI vendor id, memory, driver). Projected via `touchServerMetadata` like OS; never on heartbeat (heartbeat may send `{ resources: { ips } }` without cpus). `resolveFleetPresence` surfaces `resources`; fleet list uses summed `cores.total` / `threads.total` for inventory-strip totals and load-average normalization.

**Host Docker (`server.metadata.docker`):** daemons send a `docker` block on WS `hello` and on change-detected `heartbeat` frames **only when `/usr/bin/docker` is installed** and at least one of `docker --version` / `docker compose version` parses. Shape is `{ version?, composeVersion? }` — Compose plugin version is included when `docker compose version` works. When Docker is not installed the field is omitted from the wire and `server.metadata.docker` is left unset (not an empty object). A later Ansible `ensureDocker` is picked up on the next presence tick without waiting for reconnect. Deno WS and the Workers DO path merge it via `touchServerMetadata`; `resolveFleetPresence` surfaces `docker` (null when absent). `GET /api/client/v1/servers` returns `docker`.

**Cheap fleet index:** `listOnlineServerIds()` reads the Redis online set (Deno) or the `server.is_connected` column (Workers) — it does not fan out across all cells.

**WS upgrade flow:** JWT verified in the main isolate/process → cell `attachDaemonSocket` acquires the single-writer lease → outbox delivery is alarm-scheduled (`#pumpOutboxToDaemonSockets`; not a perpetual in-DO loop) → `detachDaemonSocket` releases the lease on close.

**DO storage schema (Workers):** SQLite tables in `DaemonCellObject` (`#ensureSchema` in `src/daemon/cell/do.ts`). One-time DDL is gated by `_cell_schema.version` (`CELL_SCHEMA_VERSION` = **2**) — Durable Object SQLite rejects `PRAGMA user_version` (`SQLITE_AUTH`), so a singleton version row is the cheap gate. `#ensureSchema` is **lazy**: the constructor restores hibernation WebSocket attachments only (no schema/version read); schema runs only on paths that touch SQLite (WS upgrade, storage RPCs, `webSocketMessage`, close/error cleanup, `alarm`). `/rpc/diagnostics` and `/rpc/liveness` must return with **zero** DO SQLite reads/writes and no alarm changes — including on a cold wake — so hibernation stays free of schema churn. When `#ensureSchema` does run on an already-initialized cell it performs **only a version read** (try `PRAGMA user_version`, else `SELECT version FROM _cell_schema WHERE id = 1`); DDL for `_cell_schema` plus the three business tables (`cell`, `lease`, `request`) runs only when the stamp table/row is missing or stale — no per-table `sqlite_master` probing and no always-throwing `ALTER`. On upgrade, `#ensureSchema` **drops the legacy `cell`/`leases`/`outbox`/`requests` tables and recreates the singular set** — safe because all cell state is ephemeral/rebuildable (daemon reconnects; `key_last_used_at` and `__direct__` are Postgres-canonical). Socket-less wakes (`checkLiveness` / `/rpc/liveness`) take `serverId` from `X-Turbopanel-Cell-Server-Id` (or RPC body) and touch zero business rows; a `server_id`-only fallback exists for header-less snapshot/alarm callers. After `#schemaReady` is set in-memory, warm storage paths short-circuit with zero SQLite; a cold isolate that hits a storage path against an already-stamped cell pays at most the version read.

The DO caches `#serverId` (and live-socket presence) once in the constructor via `#initializeFromStorage()`. Steady-state `webSocketMessage` performs **no SQLite cell writes** for hello/heartbeat/ping paths.

**Lease model:** the daemon-socket single-writer lease is **in-memory on Workers** — derived from `getWebSockets()` + `serializeAttachment().connectionId`, no persisted row; `attachDaemonSocket` still returns `{ connectionId, lease }` with the lease constructed in memory (`DAEMON_SOCKET_LEASE_MS`). Only the **delivery** lease (`DELIVERY_LEASE_NAME`, `claimDeliveryLease`/`renewDeliveryLease`/`releaseDeliveryLease`) is persisted in the singular `lease` table. `DaemonCellLease` remains `{ holder, expiresAt }`. Safety-critical single-daemon guarantee: `IdlePresence` + `ensure-single-daemon.sh` flock (see daemon `AGENTS.md`). Redis keeps `connectionId` / `connected` in the `tp:cell:{serverId}:meta` HASH because Redis has no per-connection isolate memory (needed by the Lua sweep + orphan reclaim).

**Merged request table (delivery + correlation):** one `request` row per `requestId` carries both concerns — delivery (`seq`, `delivery_id`, `delivery_status`, `retry_count`/`retry_at`, `payload_json`) keyed by `deliveryId`, and correlation (`status` lifecycle `queued→sent→acked→done/failed/expired`, `result`/`error`, timestamps) keyed by `requestId`. Ack **retains** the row (no delete) and daemon replies (`handleInbound`) mutate the correlation status. Redis keeps delivery on the outbox Stream + PEL (no `delivery_status` column) but retains the correlation record until terminal+retention for behavioral parity. See `src/daemon/cell/contracts.ts`.

**Alarm / hibernation (Workers, disconnect-first):** `#scheduleNearestAlarm` arms an alarm only for genuine pending work (deliverable/retry/inflight rows by `delivery_status`, request expiry, and terminal retention over the single `request` table) and skips `setAlarm` when the target is unchanged (`#scheduledAlarmMs` cache). No periodic stale-sweep alarm.

**Co-located daemon** (`__direct__`): stored in the `cell` table (`remote_address = '__direct__'`) so `tryAssignColocatedDaemonToInstalledOrganization` and tunnel routing still work. Co-located detection reads the Postgres projection (`src/client/servers/colocated.ts`); the projection's `remoteAddress`/`__direct__` marker now flows from **attach meta** (`#applyDaemonSocketAttach` → runtime snapshot) into Postgres rather than from the cell-row snapshot.

**Challenge stores:** enrollment and auth challenges are **stateless HMAC-signed tokens** (`src/daemon/cell/stateless-challenge.ts`). `issue()` returns a self-contained `challengeId` in envelope form `tpchallenge.v<version>.<payloadB64u>.<sigB64u>` signed with the `daemon-challenge-signing` derived key. `consume()` verifies with a **direct key lookup by embedded version** (`findKeyForVersion`) — no loop over every keyring key, no storage, no DO, no Redis key. A challenge whose version has been retired simply fails and the daemon re-requests within the 60 s TTL. Challenges are not single-use; replay is bounded by the short TTL and the daemon's Ed25519 private key requirement.

**`DAEMON_INBOUND_ALLOWED`** is defined in `src/daemon/cell/protocol.ts` (not `hub.ts`).

**Container log tail (`container-logs-request` / `container-logs-result`):** same correlated round trip as `managed-logs-request` / `managed-logs-result`. Snapshot only — never `--follow` (that would hold the Durable Object awake). Correlation rides the existing `request` row (`deriveInboundOutcome` → `{ logs }`). Output is discarded after the HTTP response; nothing is stored.

**Repository inspect (`repo-read-request` / `repo-read-result`):** same correlated round trip. The daemon answers with file contents + a directory listing; `deriveInboundOutcome` must complete the pending request or the wizard's 30s wait expires as HTTP 502.

**Fabric path observation (`fabric-paths-request` / `fabric-paths-result`):** control-plane-initiated correlated round trip, same contract as `managed-logs-request` / `managed-logs-result`. The cell never accepts an unsolicited daemon frame — every inbound envelope still requires a `requestId` that matches an outbound request. Caps: `MAX_DAEMON_WS_FABRIC_PATH_ENTRIES` (256) on `candidates[]` / `paths[]`, `MAX_DAEMON_WS_FABRIC_PATH_CANDIDATES` (8) endpoints per request entry. Correlation rides the existing `request` row (`deriveInboundOutcome` in `inbound-outcome.ts` → `{ paths }`); **no new SQLite table, column, or alarm**. Observations are not written to Postgres per tick.

**Auto-response liveness (cell ping):** the DO registers `setWebSocketAutoResponse(DAEMON_CELL_PING → DAEMON_CELL_PONG)` in its constructor (`protocol.ts` constants). The runtime answers `{type:"ping"}` with `{type:"pong"}` **without waking the DO** — this is the primary idle liveness path on Workers. The daemon's `IdlePresence` sends that wire ping after ~60 s of inbound silence; app-level `{type:"heartbeat"}` is reserved for daemon-build-commit changes **or** changed `timeSync`/`resources.ips`/`docker` facts (see daemon `AGENTS.md`). Redis parity relies on the same wire ping updating `lastSeenAt` in cell meta. **Deno/Redis coalesce skew:** `recordInbound` coalesces Redis `lastInboundAt` writes with a 10s timer-skew floor (`HEARTBEAT_COALESCE_MS - 10_000`) so a nominal 60s ping cadence still refreshes meta every minute — without the skew, early `setInterval` ticks were coalesced and a single missed ping could trip `DAEMON_OFFLINE_SWEEP_MS` (150s) while the socket was still alive. The Deno WS ping path also re-projects Postgres online when Redis or Postgres still shows offline after a false demotion (Workers DO path unchanged — auto-response never wakes the object for pings).

**Verbose cell tracing (`TURBOPANEL_DAEMON_DEBUG`):** setting `TURBOPANEL_DAEMON_DEBUG=1`/`true` (checked via `isDaemonDebugEnabled()` in `src/logger.ts`, and `#isDaemonDebug()` in `src/daemon/cell/do.ts`) enables verbose, structured tracing of the daemon cell, its storage backend, and the daemon WS message flow. The flag applies on process restart — there is no live toggle. Traced events include WS attach/detach, inbound/outbound daemon messages, `DAEMON_CELL_PING`/pong liveness, `enqueue`/`markSent`/`handleInbound` (with pending-request status transitions), delivery lease acquire/renew/release, outbox `readOutboxBatch`/`ackOutbox`, `putSnapshot`, the command pipeline's `command-dispatch → sent → ack/outcome` lifecycle (`src/lib/commands/consumer.ts`), and the correlated `createRequestAndWait`/`waitForRequest` round-trips for dev-sync, tunnel-token, public-urls apply, and addresses requests. Greppable log tokens: `cellTrace()` (in `src/logger.ts`) emits `daemon-cell event=<name> …` lines shared by both the Redis backend (`src/daemon/cell/redis/cell.ts`) and Deno WS (`src/daemon/deno-ws.ts`); the Durable Object emits equivalent `daemon-cell event=…` lines via its private `#trace()` in `src/daemon/cell/do.ts` so wrangler-captured stdout stays filterable alongside Deno logs. The correlated `createRequestAndWait`/`waitForRequest` call sites in `src/developer/dev-sync.ts`, `src/developer/tunnel-routes.ts`, `src/admin/routes.ts`, and `src/developer/routes-core.ts` also log via `cellTrace()` under the `daemon-cell` component (`request-start`, `request-enqueued`, `request-result`). Filter `command-consumer` for the command pipeline only — `src/lib/commands/consumer.ts` uses `commandConsumerTrace()` and emits `command-consumer event=<name> …` lines (`dispatch-start`, `dispatch-enqueued`, `dispatch-sent`, `dispatch-result`, `dispatch-failed`). Debug mode also emits per-call-site DO storage-op counters (`storageReads`, `storageWrites`, `storageByCallSite`) on `CellDiagnostics`, surfaced via `getDiagnostics()` / `GET /rpc/diagnostics`, incremented by the `#sql(callSite,…)` / `#setAlarm` / `#deleteAlarm` wrappers (thin pass-through when debug is off). Redis exposes equivalent counters via `#bumpMethodRoute` / `#bumpDiag`. These counters are the billing-audit baseline. Tracing is logging-only on both backends, and the DO path remains hibernation-safe (no timers, no held-open connections) per the hibernation-warning rules above.

**Enqueue-then-poll request contract:** correlated outbound work (dev-sync, tunnel-token, public-urls apply, command dispatch, managed logs, fabric-paths, repo-read) uses `createRequestAndWait` / `waitForRequest` on `DaemonCell`. `deriveInboundOutcome` must map every terminal inbound kind those waits expect — `repo-read-result` included — or the caller times out while the daemon already answered. The backend **enqueues once and returns immediately** — it must not block inside the DO or Redis cell. The **caller-side adapter** polls `getRequest(requestId)` until the `PendingRequestRecord` reaches a terminal status or the deadline (`do-registry.ts` jittered sleep on Workers; `redis/cell.ts` `setTimeout` poll in the Deno process — cost-safe there because there is no DO billing). On Workers, `#waitForRequest` inside `do.ts` is intentionally single-shot (current row only); long waits happen in the worker isolate so the DO hibernates between RPCs. Command consumer (`src/lib/commands/consumer.ts`) follows the same pattern after outbox enqueue.

**Purge:** `DELETE /api/client/v1/servers/:id` hard-deletes the Postgres row and calls `DaemonCell.purge()` to wipe all `tp:cell:{serverId}:*` keys (Redis) or DO SQLite state (Workers). Blocked for the co-located control-plane server (403). Preflight blockers today: `network` and `container` rows referencing the server (409 `server_has_blockers` via `src/client/servers/delete-guards.ts`); future service placement checks extend the same helper. After the server row is deleted, invalidates the license whose `server_id` pointed at it (both Deno and Workers — licenses are one-shot seats; even if cell purge fails). Co-located server delete remains blocked separately so the control-plane license is never removed this way.

**License invalidate (not delete):** `DELETE /api/client/v1/licenses/:id` refuses with **409** `license_has_attached_server` (bound server id + name) while `license.server_id` is set on a live (`revoked_at IS NULL`) row — delete the server first. `invalidateLicense(..., { force: true })` is the only path that sets `license.revoked_at`, revokes daemon keys on bound servers, **purges the daemon cell** (closes live Workers DO sockets; Deno/Redis rejects the next inbound frame after an active-key check), and rejects `POST /api/daemon/v1/auth/session` when the server's bound license is inactive. Cost-sensitive daemon REST (`/metrics`, `/secrets/decrypt`, `/deployments/secrets/rehydrate`) also rejects JWTs whose `sub`/`kid` no longer match an active key. Co-located control-plane license remains non-invalidateable via the API. Server rows stay until separately deleted. End users never manage licenses in the UI — seats are minted inside Add Server and retired when the bound server is deleted.

**License-tier floor is not on hello or ingest:** the hardware floor runs on `POST /auth/session` (and hosted `POST /enroll` when resources are already on file). Adding a floor read to the hello path in `deno-ws.ts` / `cell/do.ts` would open Hyperdrive on every presence tick and break Durable Object hibernation (see **Alarm / hibernation** below). Refusing `/metrics` samples would hide an incident rather than bill for it. A machine that grows past its band loses its next JWT — and with it WS, ingest, and command lease — within one 15-minute token lifetime.

**One-shot registration keys:** each license binds to at most one server (`license.server_id` + `uniq_license_server_id` partial unique index). First successful enroll latches the key; a second host presenting the same key without the persisted `serverId` is rejected (`License already consumed or invalid`). Re-enroll of the same daemon requires the on-disk `server.id` plus the original key. Deleting the server soft-revokes the license so it cannot enroll a replacement host.

**Colocated license (`this server`):** install creates one active license named `COLOCATED_SERVER_DISPLAY_NAME` (`'this server'`) and writes plaintext id/token under the daemon state dir (`/var/lib/turbopanel/license.id` + `license.token`). DB stores only the Argon2id hash. Missing disk credentials after install fail enrollment until an operator rotates/writes them — no silent Deno boot recovery. Reserved-name reject on `POST /licenses` keeps user keys from colliding with the label. See `src/lib/db/AGENTS.md` (`license` table).
